# Noon 选品运营助手设计摘要

## 状态

产品方向与第一阶段架构已确认。完整产品需求以 [`docs/PRD.md`](../../PRD.md) 为准，本文件只记录设计收敛过程中的核心方案和取舍。

## 目标

把现有“当前页面分析插件”扩展为可持续运行的选品运营闭环：每日采集商品快照，每周生成可解释候选，由买手复核，并用日志和 Bad Case 持续校准。

## 采用方案

第一阶段采用混合本地架构：

- localhost Web 工作台作为产品中心。
- 当前用户的本地 Node.js 服务负责调度、采集、规则、AI、存储、备份和通知。
- 独立 Chromium 环境读取 noon 正常渲染页面，默认无需登录。
- 现有 Chrome 插件作为所见即所得补充和页面核验入口。
- 飞书只承担系统主动通知。
- macOS Launch Agent 在用户登录后启动本地服务。

## 未采用方案

### 原生 Mac 客户端优先

暂不采用。它增加打包、签名、公证、升级和后台权限工作，但不能解决电脑关机或休眠时无法运行的问题，也不直接提升推荐质量。

### 插件继续作为产品中心

不采用。插件不适合持有定时任务、历史快照、完整复核状态、备份和审计日志。

### 在线服务优先

暂不采用。第一阶段为单用户和两个真实类目，先验证运营闭环比提前建设账号、权限和托管环境更重要。中长期通过正式在线部署扩展，不暴露 localhost。

## 核心边界

- 系统只推荐值得人工复核的候选，不决定采购。
- Ratings 是热度信号，不是真实销量。
- 透明规则决定正式推荐，AI 只解释非结构化属性和证据。
- 明确电动或明确大型商品不进入正式推荐；证据不足进入待确认。
- 每类目每种推荐最多 10 个，不凑数。
- 数据不足类目仍进入周报，但不输出正式候选，并解释原因和影响。
- 采集不绕过登录、验证码、403、429 或其他访问控制。

## 产品演进

先跑通两个可配置类目的每日采集、周度推荐、人工复核、日志和飞书闭环。只有本地安装与运维成为主要障碍时才增加 Mac 客户端外壳；需要多用户远程协作时迁移为正式在线服务。
